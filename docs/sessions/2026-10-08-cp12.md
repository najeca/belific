## Item 8 (plan only, no code): Apple token revocation on account deletion

**What Apple requires.** App Store guideline 5.1.1(v), enforced since 30 June 2022: an app that supports Sign in with Apple must revoke the user's Apple tokens when the account is deleted, with `POST https://appleid.apple.com/auth/revoke` and the form fields `client_id`, `client_secret`, `token` and `token_type_hint` (`refresh_token` or `access_token`). The `client_secret` is a short lived ES256 JWT signed with our Sign in with Apple key (the same `.p8` that `desktop/scripts/apple-client-secret.js` uses). A token must be revoked with the `client_id` it was issued to: the bundle id `com.najeca.belific` for a token from the native iPhone flow, the Services ID `com.najeca.belific.signin` for one from the browser flow. Without it the app stays listed under the person's Apple ID ("Apps Using Apple ID") after they deleted their account. Sources: [Apple, Offering account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/), [Apple news](https://developer.apple.com/news/?id=12m75xbj), [Apple forum](https://developer.apple.com/forums/thread/707364).

**What Supabase keeps.** Nothing we could use. Supabase does not call the revoke endpoint when `auth.admin.deleteUser` runs, and the request to do so ([supabase/auth #1308](https://github.com/supabase/auth/issues/1308)) was closed as not planned. It does not store Apple's refresh token. For the browser flow GoTrue hands `provider_token` and `provider_refresh_token` to the client once, in the session returned at sign in [unverified for Apple, from the issue discussions]; they are not kept server side and are lost on the first token refresh. For the native flow (`signInWithIdToken`, what the iPhone uses) there is no authorization code exchange at all, so no refresh token exists anywhere ([supabase/auth #2155](https://github.com/supabase/auth/issues/2155)).

**Does the iPhone app have the gap today? Yes (read in code, not run).** `mobile/lib/auth.ts` calls `signInAsync`, which returns an `authorizationCode`, but only `identityToken` is used and the code is dropped. The delete function removes rows and the user and never contacts Apple. So deleting an account on the iPhone does not revoke the Apple grant. The desktop has the same gap (and also drops the provider refresh token).

**Proposed fix (not built; needs your approval, an iPhone release and secrets only you can set).**
1. A small table `apple_grants(user_id uuid primary key references auth.users on delete cascade, client_id text, refresh_token_enc text)`, no client policies, written only by an Edge Function with the service role (or the Supabase Vault instead of a custom table).
2. A new Edge Function `apple-grant` called right after a successful Apple sign in with the user's JWT. iPhone: sends the `authorizationCode` (valid about 5 minutes, single use); the function exchanges it at `https://appleid.apple.com/auth/token` (`grant_type=authorization_code`, client_id the bundle id, a runtime generated client secret) and stores the returned refresh token encrypted. Desktop: sends the `provider_refresh_token` from the session it just received (stored with the Services ID as client_id).
3. `delete-account` reads the grant first, calls `/auth/revoke`, and only then deletes rows and the user. Decide fail closed (stop and say the account was not deleted) or fail open (delete anyway and log); I recommend fail closed for a failure Apple reports, fail open when the person has no stored grant.
4. Secrets (the `.p8` key contents, key id, team id) are set by you as function secrets. The client secret JWT is created at run time for a few minutes, so there is no six month rotation for this path.
5. Existing users: the one real account signed in before any of this, so no grant is stored. It cannot be revoked by us until it signs in once more after the update; until then the person can remove Belific under Settings, Apple ID, Sign in with Apple on their iPhone. This gap needs a line in the release notes or an honest line on the privacy page.
6. Tests: pure tests for the form body, a fake Apple endpoint for the Edge Function, a real check for the order (revoke before delete). The iPhone change cannot be tested on this Windows machine (decision 018).
Estimate: about one checkpoint, plus an iPhone release. Not started.

## What Supabase's PKCE callback contains, and how it is validated (condition 1)
Read from auth-js 2.111 (`_getUrlForProvider`, `_exchangeCodeForSession`) and confirmed by a real run of `signInWithOAuth` in the app:
- Apple redirects to Supabase; Supabase redirects to `redirect_to` with `?code=<code>` appended. **No OAuth `state` reaches the app** (state is between Supabase and Apple). Errors come back as `?error=…&error_description=…`.
- auth-js appends its own `sb_flow_id` to `redirect_to` only when it is tracking a flow slot; in the real run it did not (`INFO flow id in redirect_to: no`). The code handles both: if the started sign in had a flow id the callback must carry the same one; if it had none the callback must carry none.
- So a callback is accepted only when all of these hold: (1) the link is exactly `belific://auth-callback` (one trailing slash tolerated, because Windows adds one; no user info, port, hash, extra path; exactly one well formed `code`); (2) a sign in was started **in this run** (an in memory pending record, set only after the one-time backup and only for the Belific Supabase `/auth/v1/authorize` URL with provider apple and the exact redirect); (3) it was started less than 10 minutes ago; (4) it has not been used (consumed on the first matching link, including an error link); (5) the flow id matches; (6) `exchangeCodeForSession` succeeds with the verifier stored locally. A link that fails 1 to 5 is ignored (a mismatching flow id leaves the pending sign in alive, so a stray link cannot cancel a real one). A forged code that passes 1 to 5 can only fail at 6, because Supabase checks the verifier; the real check cancelled the request at the network layer and saw a quiet "could not be completed" message.
- The log gets a reason word only (`auth link ignored (no-pending)`). The link, code and tokens are never logged, never put in an error message, and the renderer's error text is a fixed sentence.

## Silent choices
- **The pending sign in is only in memory.** If the app is closed while the browser is open, the link that relaunches Belific is ignored (no pending sign in); the user starts again. This is what "started in this run" means.
- **Where the first sign in backup lives.** In main, before the browser opens, on the `auth:begin` call (so the renderer cannot skip it). Flag key `belific_first_signin_backup` in the data folder. If the backup fails, sign in does not start and Settings says nothing was changed. The folder is `YYYY-MM-DD-pre-signin` next to the daily ones; pruning only touches plain date folders, so it is kept for good (a few KB).
- **safeStorage unavailable:** the session and verifier are kept in memory only; Settings shows "This computer can't keep a sign in safely, so a sign in lasts until you close Belific." It is shown whenever encryption is unavailable (not only when signed in), so the user hears it before signing in.
- **Encrypted file names are hashed** (`secure.<sha256 prefix>.kv`) because Supabase storage keys contain characters the file store refuses.
- **A tampered or unreadable encrypted file reads as "no session"** (signed out) and is reported to the main log without content.
- **`flowType: 'pkce'` is set only on the desktop**, so the iOS client is unchanged.
- **Sign out tries the server revoke, then falls back to a local sign out** if the network call fails, so sign out always works offline. Delete account uses the existing Edge Function and then a local sign out; local data is kept.
- **Protocol registration is skipped when `BELIFIC_NO_PROTOCOL_REGISTER=1`** (the real checks set it so they never touch the real Windows registry). A dev run (`npm run desktop`) registers `belific://` to the dev Electron with the script path; the installer registers it for the installed app (checkpoint 7).
- **Test hook honesty:** the only test affordances in `main.js` are two environment variables, `BELIFIC_NO_PROTOCOL_REGISTER` and `BELIFIC_FORCE_NO_SAFESTORAGE`. The harness replaces `shell.openExternal` from outside, so no hook for it exists in the app.
- **The Settings modal is minimal:** no avatar, no name, no profile dropdown. The account line is the whole footer line, so sync status stays visible and is clickable.
- **Signed in label** is the email, or "Apple account" if Apple's private relay gave none.

## Checkpoint 6.1 (version 2.11.1): fixes from the security review

This section supersedes the earlier text above where they differ (single use consumption of the pending sign in, the encrypted verifier file, the 34 desktop tests, the real check counts).

Not changed: the sync rules of checkpoint 5 and iPhone behaviour. The only edit in `sync.ts` is a guard that returns at once when `belificDesktop` is absent (iOS) and, on the desktop, waits for the account choice (see M2). The iOS bundle export still contains none of the desktop markers.

- **M1 stray link.** `AuthGate` (authLink.js) no longer consumes the pending sign in on a link. It hands one code out at a time, and the page reports the exchange result through `auth:finish`. A failure restores the verifier from a private copy (signin.js) and counts toward 3, then it closes. Success, cancel, sign out and the 10 minute expiry also end it; an expiry timer wipes the verifier even if no link comes. A replayed code after success is ignored. No flow id was added to `redirect_to`.
- **Verifier in memory only (approved deviation from "encrypted private copy").** Keys ending in `code-verifier` never reach the disk, and neither does the private copy. A sign in only lives for this run, so a file could only be a stale leftover. **Quitting the app mid sign in abandons that sign in** (it always did: the pending sign in is memory only), and the person starts again.
- **L1.** The verifier entries are wiped on cancel, expiry, a refused or failed begin, three failures, success and sign out.
- **M2 account switching** (`lib/accountSwitch.ts`, `AccountChoiceModal.tsx`). Last user id key `belific_last_user_id` (`deleted` after delete account); a different user or any user after a delete, with local data, gets the two choices; a persisted hold key `belific_account_choice_pending` makes `runFullSync` and `onSignedIn` return until it is answered (also after a restart). A labelled `account-switch` backup is taken first; if it fails nothing changes. "Start empty" runs the existing `clearAllData` and reloads the page. No stored id (first ever sign in), the same id, or no local data proceed as before.
- **M3.** `secure.*` files are excluded from `readAll` (Export), daily and labelled backups. A failed server revoke on sign out stores `{access_token, refresh_token}` under `belific_revoke_pending` in the encrypted store; `retryPendingRevoke` runs at launch and on the `online` event with a throwaway client (`setSession` then `signOut`), and clears the entry on success or when the server says the session is already gone. Settings shows "Ending the session on the server is waiting for a connection and will retry." while it is pending.
- **L2.** `SecureStore.setItem` encrypts before anything else; on an error the value stays in memory, `persisted:false` is returned and `persistent` turns false so Settings shows the warning. `isSessionPersistent` returns false when the status call fails.
- **L3.** `desktop/src/externalLinks.js` is the allow list used by `window.open` and `auth:begin`: `uucycebkpgwbktdytxvr.supabase.co` (path `/auth/v1/authorize`), `najeca.github.io` (path `/belific/`, the privacy and terms pages of the published site) and `github.com` (path `/najeca/belific/issues`, the support link in privacy.html and terms.html). Found in: `privacy.html` line 84 and `terms.html` line 67 (the issues URL), `docs/CLAUDE.md`, `docs/architecture.md`, `docs/current-state-audit.md` and `docs/publishing-reference.md` (`najeca.github.io/belific/`). The app itself and `app.json` contain no web links. **Any future marketing site domain must be added to the allow list.**
- **L4.** The kv IPC refuses `secure.*` and `belific_first_signin_backup`; labelled backup folders get `-2`, `-3` instead of being replaced; `auth:begin` is refused (`busy`) while a sign in runs. The Sign in button first cancels the old attempt, so a deliberate retry works, and it is no longer disabled while a sign in is open.
- **L5.** CSP gained `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`. A dev mode CSP was **not added**: it is not simple (Metro needs eval and a websocket to `localhost:8081`), and dev runs on a separate data folder.

### Known limits
Informational items from the security review (not acted on): **the review's informational list was not included in the request for 6.1, so it still needs to be pasted here.** What is known from this checkpoint:
- A stray link can still make the page show "Still waiting for you to finish signing in" while a real sign in is pending; it does not harm it.
- A sign in abandoned by closing the app is not resumed; the link that launches Belific afterwards is ignored.
- The revoke retry uses the global scope that `signOut()` uses by default, so it also ends the iPhone's session, as a normal sign out does.
- No dev mode CSP.
- The verifier lives in main memory, so a compromised main process could read it; the page (renderer) can read and write session keys through `secureKv`, as it must for auth-js to work.

Unverifiable without a live Apple sign in (Jethro's setup first): the Apple round trip itself; the same `sub` as the iPhone; whether Supabase's redirect allow list needs `belific://auth-callback**`; whether Supabase appends `sb_flow_id` in the real redirect; the delete-account function with the `app://belific` origin; the revoke retry against the real logout endpoint and real token expiry; that Windows hands the `belific://` link to the running instance in the installed app.

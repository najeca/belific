## The conflict rules, and what each pass compares (condition 2)
- **Pushes compare nothing.** The client sends the queued row; the server's trigger stamps `server_updated_at` with the server clock. Whichever device's push arrives last is the server's current version. A live row never carries `deleted_at`, so a push cannot undelete. Upload batches are split by column set (`groupByColumns`), because PostgREST fills a column a row leaves out with NULL.
- **Incremental pulls** fetch rows with `server_updated_at >= cursor − 5 s` (the server clock), ordered by `server_updated_at` then key. For each pulled row:
  - a tombstone wins and cancels a pending local edit of that row;
  - a row with a pending local change (still in the outbox) keeps the local version, which is about to be pushed and will then be the newest on the server;
  - a local tombstone the server shows alive is kept and pushed again;
  - otherwise the server row replaces the local one.

  No timestamps are compared, because server order already says which change is newer. The cursor is the largest `server_updated_at` seen, stored only after the merge is saved.
- **The first full pass** compares `Date.parse(local.updatedAt)` with `Date.parse(remote.updatedAt)`. It applies on the first sync after sign in, the first sync after upgrading to 2.9.0, and every pull on a server without `server_updated_at` (before migration 1). In those passes a local row may have changed without ever going through the outbox (written while signed out, or by the 2.1.0 code), so it is neither pending nor known to the server's order. Those rows are compared by their `updatedAt`, parsed, never as strings: equal instants written as "…Z" and "…+00:00" are equal, which fixes V7d's endless re-upload. Local rows the server lacks are uploaded, and server rows the device lacks are downloaded. Pending, tombstone and live rules are the same as above.
- **Why the other passes need no timestamps:** after the first pass, every local change is in the outbox, and every remote change arrives in server order. "Pending local, else server" then gives the same answer as comparing times when clocks agree, and the right answer when they don't (tested with a clock one hour fast).
- **Routine completions** (hard deletes, no timestamps) are pulled in full every sync, paginated (a small table). A local completion missing from the server is:
  - kept if an add is pending;
  - dropped if this device had seen it on the server (deleted elsewhere, V7a);
  - uploaded if it was never seen.

  `seen` is updated from every pull and every successful push or delete. A server completion missing locally is added unless a delete is pending.

## First sign in with data on both sides (condition 1)
The desktop creates rows while signed out (nothing is queued). The server already has the iPhone's rows. On sign in, `onSignedIn` turns the outbox on and runs a sync with no cursor, so the first full pass applies:
- local-only rows are uploaded, tombstones included, so a local delete is never lost;
- server-only rows are downloaded;
- same-id rows go to whichever has the later `updatedAt`, parsed;
- rows are keyed by id, so nothing is duplicated.

Test `first sign in with data on both sides…` in `syncEngine.test.ts` covers every case: a phone-only row, a desktop-only row, a desktop-only tombstone, a same-id row newer on the server and a same-id row newer on the desktop. It checks both devices end with the same five ids and nothing else. The same pass runs for existing signed-in iPhones on their first launch of 2.9.0.

## Trade-off: a long offline device can overwrite a newer edit (condition 4)
"A pending local change beats a pulled live row" means:
1. Device A edits a task while offline.
2. Device B edits the same task later, online.
3. A reconnects, and A's older edit is pushed last and wins, row level, with no field merge.

Comparing `updatedAt` instead would flip that case but break under clock skew and lets a device with a fast clock win every conflict. Deletes are not affected: a tombstone always wins.

How often for one person: it needs the same row edited on two devices, with the earlier edit made while that device was offline and still unsent when the later edit happened. Phone in a dead zone or flight mode, then the same task changed on the desktop before the phone reconnects. Estimate: a few times a year at most. The visible effect is the older text or Day reappearing on that one task. Accepted and recorded in decision 013 item 7.

## The app before and after the migrations
- **Probe:** each sync first runs three cheap selects (`tasks.server_updated_at`, `tasks.duration_minutes`, `projects.color_key`, each `limit 1`). Postgres error `42703`, PostgREST `PGRST204` or "column … does not exist" means "not there". Any other error stops the sync with a recorded error, and nothing is written.
- **Before migration 1:** every pull is a full paginated pull (ordered by key, `.range()` pages, paging until an empty page so a lower row cap cannot truncate). Conflict rules as in "first full pass". Pushes work as normal.
- **Before migration 2:** the new columns are never sent (a push would fail otherwise). A pull keeps each local row's durations, times, repeat settings and colours, because the server copy lacks them. When the probe first sees the columns, every local task and label that has such values is queued once, and the next push uploads them. Tested: `a server without the new columns: …`.
- **After both:** incremental pulls by cursor; all fields sync.
- **Old iPhone builds (2.1.0)** keep working throughout. They `select('*')` and ignore unknown columns. Their upserts only send their own columns, which supabase-js merges, so they leave the new columns alone. The trigger stamps their writes, so new clients see them in order. Two old-build behaviours remain until people update: a 2.1.0 upsert sends `deleted_at: null`, which can undelete a row (the new client then pushes its tombstone again; tested), and the old string timestamp comparison.

## Choices and deviations
1. **Conflicts: last to reach the server wins**, not client `updatedAt`. This deviates from decision 013 item 3 and from the review, which kept updatedAt LWW. Reason: skew-proof, simpler, and it matches the brief's "comparing server time". So there is no clock-skew warning in the status.
2. **Completions use a "seen on server" set** instead of `lastFullSyncAt` (013 item 4); `lastFullSyncAt` breaks when the completing device's clock is ahead.
3. **Cursor overlap of 5 s** (`now()` is the transaction start, so a row can commit after a later stamped one); re-applying rows is harmless.
4. **Pull before push** in every sync, so a delete from another device cancels a stale pending edit before it is sent. Writes between syncs are pushed 1.5 s after they happen.
5. **The outbox only runs while signed in**, and sign out empties it and clears cursors, the seen set and caps (so another account starts fresh). Existing signed-in iPhones turn it on at their first sync of 2.9.0.
6. **Column naming and constraints:** `projects.color_key`, not `color` as in the review. Migration 2 has **no CHECK constraints**; the client sanitises (`sanitizeDuration` 1 to 1440, `sanitizeTime` HH:mm, `sanitizeRule`, `sanitizeDays`, `sanitizeMonthDay` 1 to 31 → otherwise NULL), because one bad row would fail a 500 row batch and stall sync.
7. **Migration 1 adds `server_updated_at` to `routine_completions` too**, as the review's plan says, though the client still pulls that table in full.
8. `create or replace trigger` (Postgres 14+) instead of a drop and create, so the migration files contain no drops. The trigger function pins `search_path = ''`.
9. **No iOS UI for status** (013 item 6 suggested Settings); the brief asked for no new UI beyond the desktop line. The status object exists for it.
10. **Recolouring a label is now a stamped edit**, since the colour syncs. The lazy fill still does not touch `updatedAt` (4.1 rule) but is queued.
11. **The Electron window-focus IPC trigger (013 item 5) is not built**: react-native-web `AppState` follows page visibility, and the 120 s poll runs while the window is visible.
12. **`devSeed.ts` (dev builds only) still writes directly**, unqueued, so its fake events never sync (N7).
13. **V7i (delete-account not atomic) is unchanged**: still table by table with an early return, and the `on delete cascade` on `user_id` removes anything left when the auth user goes. The `auth.ts` comment that claimed "atomically" is corrected.

## Shared with Landis and Proload
Since the move, Belific, Landis and Proload use one Supabase project (`vlogfwnmaqorhialcqbr`). The data is separated by schema (`belific` here; the others use their own), but a lot is project wide. A change made for one app changes all three:

| Shared thing | What it means for Belific |
|---|---|
| **Auth users** | One `auth.users` table. The same Apple or Google person is one user across the apps. Deleting the auth user would delete that person's data in every app (their tables cascade on `user_id`). Belific's delete-account therefore does not delete it. |
| **Provider settings** (Apple, Google, others) | One Apple provider and one Google provider for the project. Enabling, disabling or changing a client ID or secret affects every app. |
| **Redirect URLs and Site URL** | One allow list (Authentication, URL Configuration). `belific://auth-callback` must be added and the other apps' entries must stay. Never change the Site URL for Belific. |
| **Email templates and SMTP** | One set. Belific has no email sign in yet (2.19.0 is planned); when it does, its emails use the shared templates and sender, so the wording and sender name cannot be Belific only. |
| **Password rules and other auth settings** | One minimum length and set of requirements, one rate limit set, one session length (JWT expiry). Email and password sign in in Belific (2.19.0) must follow whatever the other apps need. |
| **Apple Client IDs field** | One comma separated list. It **must keep every app's IDs**: Belific's `com.najeca.belific` (native iPhone sign in) and `com.najeca.belific.signin` (desktop Services ID), plus the ones Landis and Proload already use. Removing another app's ID breaks that app's Apple sign in. |
| **Apple secret key (OAuth secret)** | The provider has a single secret field. That secret is a token made for **one** Services ID. Native iPhone sign in (`signInWithIdToken`) does not use it, but browser sign in (the Windows app) does. If Landis or Proload also use a browser flow with their own Services ID, one secret may not fit both. **Unverified**: how the shared project handles this, and which Services ID the existing secret was made for, has not been checked. Find out before changing the field. |
| **Google OAuth client** | One client ID and secret in the provider. The redirect URI list of that Google client must contain the callback URL for this project. |
| **Edge Functions and secrets** | Function names share a namespace in the project. `delete-account` must not collide with another app's function of the same name. **Unverified**: whether one exists. |
| **Quotas and backups** | One database, one set of limits, one backup. A mistake in one schema can be restored only for the whole project. |

### Switching projects on a device
The app stores a project fingerprint (host and schema) with the sync state (`mobile/lib/projectGuard.ts`). On the first start against the new project, or whenever it differs, the device signs out locally, forgets the sync cursors and the outbox, ends any pending sign in, and keeps all local data. The next sign in counts as a different account, so on the desktop the existing account choice asks whether to upload this computer's data or start empty (a backup is made either way). The iPhone has no such prompt: its first sign in uploads its local data.

The phone's own callback rules and flow are in `lib/phoneAuthCore.ts`, `phoneGoogleFlow.ts`, `phoneGoogleAuth.ts` (tested with fakes). Hermes has no `crypto.subtle`, so auth-js would send a **plain** PKCE challenge; the phone installs `@noble/hashes` (pinned 1.8.0) as the digest, and the browser opens only if the challenge is S256 **and** the verifier came from secure randomness (`crypto.getRandomValues`, which auth-js uses unless `crypto` is missing altogether; checked at run time never to touch `Math.random`, and the stored verifier must hash to the URL's challenge). `app/+native-intent.ts` keeps expo-router from treating the callback as a screen.
- **Phone sign out and Delete account use scope local only** (`signOutThisDevice`), so the phone never signs out the desktop, Landis or Proload. Tested: every `auth.signOut(` call in the app asks for the local scope, and no `scope: 'global'`/`'others'` or `auth.admin` exists in the app code.
- **First launch of a new build:** the project guard runs on the phone too. From 2.1.0 it finds no state, writes the fingerprint and resets nothing; the old Apple session is stored under the old project's key, so the phone shows signed out. There is **no account choice and no backup on the phone**: the first sign in uploads and merges (additive, nothing local is removed). Make an encrypted device backup first. Upload is 500 rows per request with a persisted outbox, retried with backoff; **the phone shows no sync status**. Same-name labels from the phone and desktop stay two labels; the 2 routines are not converted automatically.
- **Apple on the phone** finds or creates an Apple user; it reaches the same user as Google only if Supabase links the identities (same verified real email; unverified) or after the later "Add a sign in method" feature. Until then the phone's Apple button can give a separate user. Client IDs for `com.najeca.belific` must be appended, never overwrite other apps' entries.

Details and the by-hand checklist: `docs/build-progress.md`. Decision 028.
- **The timer:** one at a time; a timer over 24 hours asks before anything is added; it is read from the stored tasks, so it survives a restart; it shows on the other device after a sync. Whole minutes, rounded down, a future start counts 0. Nothing in this is verified between two real devices yet.
- **The layout is read once at start** and is the last write wins between devices; two screens of different sizes share it.
- **The Calendar takes no drops.** Giving a task a time is dragging it onto the Timebox. Only the Timebox, not the Calendar, can be dragged into.
- **Not done in phases 2 and 3:** emoji in the Settings, Labels and Progress pages; the plan's Ctrl+I, Shift+T, Shift+B and Left and Right between days; a Trash view (a deleted task is a tombstone, restore is phase 6); repeating in the details panel (phase 4).
- **Real checks** (Electron with real input, isolated data folder, fake Supabase): `desktop/test/real/p2.js` (42) and `p3.js` (52), after `node desktop/scripts/build-web.js`. The older `cp6` to `cp12` still pass.
- **Streaks (2.17.0, decision 007) are derived, never stored.** `mobile/lib/seriesStreak.ts` works them out from the stored occurrences, the skip tombstones and, for a converted routine (`rt_<id>`), the old routine completions. A line "N days in a row" ("N in a row" for other rules) shows on TODAY's card and in the block popover from 2 only; the Progress page (profile menu or File, Progress) lists every live series. Skipped days are neutral, a day not done ends the run silently, today before it is done is neutral. "Show streaks" (Settings, Planning) hides the lines, not the page. Desktop only: the iPhone shows no streaks until the iOS catch-up release.
- **Google sign in (2.18.0, checkpoint 12, decision 026) is code only.** The desktop has a Sign in page (profile popover or Settings, Account, Sign in) with Continue with Apple and Continue with Google; nothing works until Jethro does `docs/GOOGLE_SIGNIN_SETUP.md` (and `docs/APPLE_SIGNIN_SETUP.md` for Apple). Tested only against the in process fake Supabase with fake provider pages; no real Apple or Google round trip, no live dashboard. **The delete-account function in the repo was changed (no user id in logs, no raw errors) but is NOT deployed.** An Apple and a Google sign in by one person can end as two accounts (Apple private relay): `docs/ACCOUNT_LINKING_TEST.md`. Apple token revocation on account deletion is a known gap on both apps, see `docs/sessions/2026-10-08-cp12.md`.
- **Unverified claims on the public pages (privacy.html, terms.html, effective 8 October 2026):** (1) Supabase EU West (Ireland) for the data (stated since 2.15.0, from Jethro, not checked here); (2) Google sign in keeps the Google email, name and profile picture address with the account (Supabase default behaviour, from memory, not tested); (3) the app asks Google only for basic profile and email (the scopes are chosen in the Google console setup, not yet done); (4) Google sign in works only on Windows and Apple on both (true of the code); (5) the Windows session is encrypted with Windows (tested on this machine only); (6) the terms sections 4 and 5 (no warranties, limitation of liability) are old legal wording nobody has reviewed as law.
- **A rule change is retroactive.** Streaks use the series' CURRENT rule for the whole history. Changing Mon/Wed/Fri to every day makes the past off days count as not done, and the run ends there, silently. Nothing is stored that could say what the rule used to be.
- **A stale device can show a different run for a moment.** A device that has not synced and ticks a projected day (decision 023's known limit) or has not yet received another device's ticks computes from what it has; after a sync both agree.
- **History window.** Runs look back 366 days (best run is the best within that). Skip tombstones of series days are kept 400 days locally (`series.OCCURRENCE_TOMBSTONE_KEEP_DAYS`) so a skip never ages into a miss; the server never prunes them. Ordinary tombstones still prune at 90 days.
- **A series restarted after Does not repeat** counts its old history, and the days in between as not done.
- **The iOS marker gate** is `npm run check:ios-markers -- <export folder>` in `mobile/` (after `npx expo export --platform ios --output-dir <temp folder outside the repo>`). It exits 1 on any marker, 2 on a missing folder or bundle. `copyRoutineCompletions` is the one allowed name (inert helper in the shared `storage.ts`, checked in source by `git grep`). **`seriesStreak` is a marker only until the iOS catch-up release reuses the streak code: whoever ships the phone feature must remove that marker from `mobile/scripts/ios-markers.js` deliberately, and say so in the commit.**

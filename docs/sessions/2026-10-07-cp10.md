## Findings before building (Jethro's addition 1)

**1. How the phone shows stale incomplete rows from a series.** `getTopTasks` and the Tasks screen (`sortTasksForDisplay` in `lib/data.ts`) show every stored, non deleted task. An incomplete task whose Day is today or earlier sorts FIRST, then High priority, then oldest `createdAt`. Nothing caps or hides an old overdue row, so a series root row that is never completed stays at the top of the phone's Top 3 and Tasks list with its old Day. It does not break desktop projections (the desktop ignores past stored rows, decision 023) and creates no rows. Cost: after a conversion the phone shows the root row `rt_<id>` as one ordinary task (with its date), and, because the routine is tombstoned, no routine. A converted routine's root row is dated the conversion day and, if never ticked, looks overdue on the phone afterwards. Converted series made from routines are oldest `createdAt` (the routine's), so they sort ahead of newer tasks. Accepted, documented, and the reason the button waits for the iOS catch-up release.

**2. Does the phone's `createNextOccurrence` interact with desktop projections as decision 023 says?** Yes. Completing a dated repeating task on the phone calls `createNextOccurrence`, which makes `rootId:<next day>` only if no row (live or deleted) has that id, counting from the later of the task's Day and today. A stored row is a "taken" day for the desktop, so the desktop never projects a second card on it. The phone copy carries the rule, reminder and subtasks (unticked, ids `${id}:sN`), so it is a valid template too. No duplicate rows, no broken projections. Two devices completing on different days could create two next rows (already documented, accepted).

## Finding that changed the design (flagged, not in the approved plan)

**A tombstone can never be cleared by sync.** `withDeleted` in `lib/syncCore.ts` only ever sends `deleted_at` for a tombstone ("a live upsert never clears one"), and `mergeRows` makes a pulled tombstone win over any live version and re-pushes a local tombstone over a live server row. So "Undo revives the routines" cannot work under the same ids: the next pull would put the tombstone back. What is built instead:

- Convert tombstones the routine (a direct write) and writes the series `rt_<routineId>`.
- Undo ends the series (`deleteSeriesRows`: open rows tombstoned, finished days kept and no longer repeating) and gives each routine back as a **new** routine row (same title and time of day, new id), with that routine's completions **copied** to the new id (added, never removed, same `completedAt`). The old routine rows and the old completions stay as they were.
- Because ids differ, converting again after an Undo converts the new rows; it can never collide with an ended series.
- A routine whose series row already exists (half finished conversion, or the person ended or deleted the series) only gets its tombstone; no second series is written.

If Jethro would rather change the sync rule so a newer live row can beat a tombstone, that is a sync change for every table and for the already released iPhone 2.1.0 (which keeps its own tombstone and re-pushes it), so it was not done here.

## Account switch (addition 2)

`storage.clearAllData` already removed `belific_routine_completions` (and the seen completions bookkeeping). The gap was `DATA_KEYS` in `desktopAuth.ts`, which feeds `hasLocalData` (whether a different account must choose between uploading and starting empty): it lacked the completions key. It is now `USER_DATA_KEYS` in `lib/accountSwitch.ts` with a test that it contains every user data key `clearAllData` removes (read from `storage.ts` as text) and that a computer whose only data is completions counts as having data.
